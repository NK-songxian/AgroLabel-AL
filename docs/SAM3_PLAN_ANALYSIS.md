# SAM3 方案可行性分析（PlantSeg-34 基线）

> 结论先行：**方向对，但截图方案里有 3 处事实错配，直接照做会白跑。**
> 建议先做"基础 SAM3 零样本上限测试"，再决定是否替换 YOLO。

---

## 1. 三处必须先纠正的事实

### 1.1 34 类不是"病害"，是植物物种

截图里的 `disease_prompt_bank.json`、`dark brown necrotic spots`、`Early blight`
全部对应 **115 类版本**（植物 + 病害）。我们主实验的 34 类 `names` 是：

```
Apple, Banana, Basil, Bean, Bell pepper, ... Tomato, Wheat, Zucchini
```

**是宿主植物物种，没有一条病斑类别。** 若沿用病害提示词，提示语义与标签语义完全错配，
预标注会直接失效。

→ 已重建：`configs/species_prompt_bank.json`（34 条物种概念提示）。

### 1.2 每张图只含 1 个类别

对 train 随机抽样 300 张统计：**跨类图像 = 0**，全部单类别、多实例（密集冠层）。

推论有三条：
1. 不需要每图跑 34 次提示。用该图类名提示一次即可 → 成本从 O(34N) 降到 O(N)。
2. 34 路分类不是瓶颈，**实例分离才是瓶颈**。
3. 用"真值类名"提示是 **oracle 协议**，是上限基准，不能当作可上线的预标注结果。

### 1.3 SAM3 不做 34 类判别

SAM3 是"概念分割"，你给 `basil leaf` 它就找 basil，不会告诉你这张图是 basil 还是 lettuce。
所以在 oracle 提示下它的指标天然偏高（不会产生跨类误检）。
真实部署必须有一步**类判别**（CLIP 检索 / 34 提示仲裁 / 或直接复用 YOLO 的类别头），
这一步才是真难点，也是我们后面能做出差异的地方。

## 2. 指标口径：别拿 DSC 和 mAP 直接比

截图提到 ReLeaf-SAM 在 PlantSeg 上报 **81.05% DSC**。注意：

| 指标 | 含义 | 我们的数 |
|---|---|---|
| DSC / Dice | 掩码重叠度，只算匹配上的实例 | YOLO 基线未测（需补） |
| mask mAP50 | 逐类 AP 后平均，含漏检/误检惩罚 | YOLOv8n-seg = **0.287** |
| mask mAP50-95 | 更严的定位要求 | YOLOv8n-seg = **0.140** |

**DSC 81% 与 mAP50 0.29 不是同一把尺子**，不能据此说"YOLO 差 50 个点"。
公平比较必须补 Dice，并同时报 mAP。

---

## 3. 基础 SAM3 会不会"比 YOLO 好很多"——预判

先说结论：**分指标看，不会全面碾压，但会赢在边界质量。**

| 维度 | 预判 | 理由 |
|---|---|---|
| Dice / 边界贴合 | **显著优** | 848M vs 3.2M 参数；SAM 系天生强边界 |
| mask mAP75 | **优** | 高 IoU 阈值下差距最大 |
| mask mAP50 | **持平或小胜** | 密集叶片实例分离是 SAM 弱项，过分割/粘连会压分 |
| 推理速度 | **差 10–50×** | 单图 0.3–1s vs YOLO 毫秒级 |
| 可训练性 | **差** | 无 34 类头，不能端到端微调对齐我们的标签 |

这个预判本身就是有价值的实验结论：它能量化"基础模型在农业密集冠层上的天花板在哪"，
正是论文里"为什么要做我们的方法"的立论依据。

## 5. 对"创新点"的判断

截图把创新落到"让基础模型知道自己什么时候分错，并主动找最有价值的纠错样本"——
**这个方向是对的，而且它就是 VARD-AL 的延伸，不需要另起名字。**
但"跨提示一致性校准 + 病斑质量约束 + 实例筛选"里：

- ❌ "病斑质量约束" 对 34 类不适用（无病斑）。
- ✅ "跨提示一致性" 可改造成 **物种提示一致性**：同一类用 2–3 个变体提示
  （`basil` / `basil leaf` / `a basil leaf`），掩码 IoU 分歧 = 不确定性信号。这是可测的。
- ✅ "实例筛选" 改成 **掩码质量分**：边界稳定性、面积合理性、与 YOLO 框的吻合度。

这三者可合成一个 **预标注可信度分数**，直接喂给 AL 采样器 —— 与赛题 25 分（主动学习）
和 30 分（预标注质量）都咬得上。

## 6. 落地顺序（先基础，后创新）

| 阶段 | 内容 | 产出 | 判据 |
|---|---|---|---|
| **P0** | SAM3 零样本，oracle 提示，val 200 张冒烟 | 跑通 + 可视化 | 无报错、掩码合理 |
| **P1** | SAM3 val 全量 → Dice / mAP50 / mAP75 / 逐类表 | `runs/sam3_zeroshot/val/` | 与 YOLO 0.287 对比 |
| **P2** | 去 oracle：加类判别（CLIP 或 YOLO 头） | 真实预标注指标 | 掉多少点 |
| **P3** | 跨提示一致性 → 不确定性 → AL 采样 | AL 效率曲线 | 同标注预算下 mAP 更高 |
| **P4** | YOLO + SAM3 混合（YOLO 出类别/框，SAM3 refine 掩码） | 最终方案 | 兼顾精度与速度 |

**P0/P1 做完就能回答"要不要换"这个问题，不必等创新模块。**

## 7. 已知风险

1. **权重 gated**：官方 `build_sam3_image_model()` 默认从 HF 拉取，需申请权限。
   我们已有本地 `sam3.pt`，脚本走 `load_from_HF=False` + 本地路径，绕过该限制。
2. **版本强绑定**：官方要求 Python ≥3.12 / torch ≥2.7 / CUDA ≥12.6。
   Pro6000 是 Blackwell，必须 cu128 轮子。
3. **不得影响其他进程**：环境建在 `/root/autodl-tmp/Ryan/envs/sam3`（独立前缀），
   所有产物写 `/root/autodl-tmp/Ryan/` 内，不碰全局 python 与已有任务。
4. **数据 16G**：上传耗时最长，建议先只传 `labels/` + `images/val` 做 P0/P1，
   全量训练数据按需再传。

## 8. 一句话总结

**先用 15 分钟把 SAM3 在 val 上跑出一张 Dice/mAP 表，再决定要不要改技术路线。
在没这张表之前，"SAM3 是不是更好"只是猜测。**
